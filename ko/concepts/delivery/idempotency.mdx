---
title: "멱등성"
description: "이벤트를 게시하거나 수신할 때 부수 효과가 중복으로 발생하지 않도록 합니다."
---

Relaybox는 모든 이벤트를 *최소* 한 번 전달합니다. 따라서 엔드포인트가 같은 이벤트를 두 번 받는 경우가 가끔 있습니다. 예를 들어 서버가 이벤트를 처리했지만 Relaybox가 `200` 응답을 확인하기 전에 연결이 끊어진 경우가 그렇습니다. 멱등성을 갖추면 이런 상황에서도 고객에게 요금이 두 번 청구되는 일을 막을 수 있습니다.

멱등성은 두 가지 측면에서 고려해야 합니다.

## 게시할 때 {#when-publishing}

서비스와 Relaybox API 사이에서도 네트워크 오류가 발생할 수 있습니다. 게시 요청이 시간 초과되면 이벤트가 수락되었는지 알 수 없습니다. `Idempotency-Key` 헤더를 함께 보내면 언제든 안전하게 재시도할 수 있습니다:

```bash
curl https://api.relaybox.dev/v3/events \
  -H "Authorization: Bearer $RELAYBOX_API_KEY" \
  -H "Idempotency-Key: checkout-ord_8Hx2kP-paid" \
  -d '{"type": "order.paid", "payload": {"order_id": "ord_8Hx2kP"}}'
```

Relaybox는 최근 24시간 이내에 이미 받은 키가 다시 들어오면 새 이벤트를 생성하지 않고 원래 이벤트를 반환합니다.

<Info>
  같은 멱등성 키를 **다른** 본문과 함께 재사용하면 `409 idempotency_conflict` 오류가 반환됩니다. 자세한 내용은 [오류](/ko/api-reference/errors)를 참고하세요.
</Info>

## 수신 측 {#when-receiving}

모든 전송에는 `Relaybox-Event-Id` 헤더가 포함됩니다. 처리한 ID를 저장해 두고 이미 받은 ID는 건너뛰세요:

```python
def handle(event):
    # ID가 이미 있으면 INSERT가 실패하므로 동시에 실행되어도 안전합니다.
    inserted = db.execute(
        "INSERT INTO processed_events (id) VALUES (%s) ON CONFLICT DO NOTHING",
        [event.id],
    ).rowcount

    if not inserted:
        return  # 이미 처리된 이벤트: 중복 전송된 경우입니다.

    fulfill_order(event.payload["order_id"])
```

<Tip>
  ID는 Relaybox가 재시도할 수 있는 기간 동안만 보관하면 됩니다. 기본 재시도 일정 기준으로 약 이틀입니다. 매일 한 번 실행되는 정리 작업이면 충분합니다.
</Tip>
