障害は避けられないものです。Relaybox は、お客様側で数時間のダウンタイムが発生しても、イベントを 1 件も失わないように設計されています。

## 短時間の障害が発生した場合 {#during-a-short-outage}

{maxRetryWindow}未満の障害であれば、特に対応は必要ありません。Relayboxが[自動的に再試行](/ja/concepts/delivery/retries)し、エンドポイントが復旧した時点ですべてのイベントを配信します。

<Tip>
  データベースの移行など、障害が発生することが事前にわかっている場合は、あらかじめ[エンドポイントを一時停止](/ja/concepts/endpoints#endpoint-states)しておきましょう。イベントはキューに蓄積され、再開時に順番どおり配信されるため、再試行回数を無駄に消費せずに済みます。
</Tip>

## 長時間の障害が発生した場合 {#after-a-long-outage}

エンドポイントの停止期間が再試行期間を超えた場合、一部のイベントは **failed** としてマークされます。復旧後に、これらのイベントを再送してください。

<Tabs>
  <Tab title="ダッシュボード">
    1. エンドポイントを開き、**Failed** フィルターを選択します。
    2. 障害が発生していた時間範囲を選択します。
    3. **Replay all** をクリックします。送信されるイベントの件数が表示され、確認を求められます。
  </Tab>

  <Tab title="CLI">
    ```bash
    relaybox events replay \
      --endpoint ep_5Np8Wz \
      --status failed \
      --since "2026-10-18T02:00:00Z" \
      --until "2026-10-18T09:30:00Z"
    ```
  </Tab>

  <Tab title="API">
    [イベントの再送](/ja/api-reference/events/replay)を参照してください。
  </Tab>
</Tabs>

## アラートを受け取る {#get-alerted}

障害を顧客からの報告で初めて知る、という事態は避けましょう。**Settings → Alerts** で、通知を受け取る条件を選択します。

| アラート                  | 発生条件                                   |
| --------------------- | -------------------------------------- |
| **Failure rate**      | 5 分間に失敗した試行の割合が、指定した値を超えた場合            |
| **Backlog**           | エンドポイントで最も古い保留中のイベントが、指定した時間を超えて滞留した場合 |
| **Endpoint disabled** | 5 日間失敗が続き、Relaybox がエンドポイントを無効化した場合    |

アラートの送信先には、メール、Slack、PagerDuty、または任意の Webhook URL (Relaybox のエンドポイントを含む) を指定できます。

<Warning>
  監視対象と同じインフラストラクチャに依存するエンドポイント*だけ*をアラートの送信先にしないでください。そのインフラストラクチャがダウンすると、障害に気付けなくなります。
</Warning>
